# Local settlement operation and recovery

Use only the disposable synthetic shop. All settlement screens are admin-only. A confirmation records what an operator says happened; the application does not send, verify or cancel external money. PDFs, attachments and cashier billing remain disabled.

1. Open **Settlements** or the settlement link on a customer, supplier or invoice. Review source eligibility and current availability. Unknown/reconciliation-required sources cannot be spent. Customer advances are recorded once as incoming receipts; an existing advance or unapplied return credit can be allocated across selected same-customer invoices. Review target due and source remaining values before confirming.
2. Record a refund only against available source value. Already allocated value requires an explicit allocation reversal first. Enter exact concrete cash/UPI/bank/cheque portions and confirm the observed outgoing event. Anonymous liabilities live on their own screen and reference the original sale/return; no customer account is fabricated.
3. For suppliers, recognize an acknowledged payable against a verified receipt with reference, due date and reason. A received purchase is not automatically unpaid debt. Apply the same supplier's debit note, record an actual supplier payment, or record an actual supplier refund against a claim. These actions do not move stock again. Read current remaining payable/claim values, not the original debit note's stored issued status.
4. Reversals preserve originals and create explicit full compensating evidence. They require a strictly later open business date and cannot silently unwind dependencies. Cash reversal means recording the confirmed opposite cash event with the original tender split; it does not reverse a provider transfer. If the real correction uses another route/split, stop that unsupported case for reviewed policy rather than misrecording it.
5. Use effective-date statements and as-of availability/aging. Opening and running balances precede page/filter slicing. Collections use actual dated tender portions; applying yesterday's advance today creates zero collection today. Reports distinguish incoming customer money, refunds, supplier cash, sales, returns and profit. An unverified warning means totals are not reconciled evidence. CSV/XLSX exports neutralize formula text; no PDF shortcut is available.
6. Enter the first day's explicit counted opening float. Later openings follow the prior close one day at a time. Review expected cash against physical counted cash and explain any discrepancy. Closing locks that day and all earlier dates. Discrepancy remains a review item and creates no balancing entry. Corrections use later open dates; do not edit closed evidence.

If a response is lost, reload or reauthenticate and use **Recover** for the saved operation. The browser retains the original actor, operation, exact payload, source/target identifiers and key before dispatch. Account switching must not create a new operation for the unresolved intent. Return to the original actor/document when indicated. A later rejection does not prove an earlier uncertain attempt failed. Do not clear browser storage, fabricate a replacement receipt or retry with a fresh key to resolve uncertainty.

Database recovery is forward-only: preserve original source, immutable application/refund/debit/cash/ledger rows and successful idempotency results. Use read-only `db/reconciliation/phase-4.sql`, compare the exact failing key/actor with saved results, and investigate inconsistent evidence. Do not rewrite issued snapshots, rebalance caches or roll back to older code that ignores settlement/period rules. Live backups, restoration and accountant acceptance remain separate mandatory gates.
